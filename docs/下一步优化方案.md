## P0-1 视觉问答修复（语音 + 网页都无效）

### 诊断

两个独立原因：

1. **语音链路**：`vision_assistant.py` 的 `VISION_PHRASES` 关键词表覆盖不全。
   用户自然说法如 "你看到了吗"、"你能看见我吗"、"看得见东西吗"、"你眼里有什么"
   都**不在表中** → 未命中拦截 → 落入 DeepSeek 纯文本 LLM → 模型只能回答"我看不到"。
2. **网页链路**：`dashboard.py` 的 `/api/chat` 只调用 `LlmDialogue`（DeepSeek 纯文本），
   **从头到尾没有接视觉模块**——不是 bug，是当时为控制改动范围留下的缺口。

### 方案

**A. 扩充触发词 + 双保险判定**

- 补充短语：`你看到了吗`、`你能看见`、`看得见`、`你眼里`、`眼中的`、`识别一下`、`辨认`、`这是什么`（需谨慎，"这是什么"可能指物体）、`你面前的`、`镜头里`、`画面里` 等。
- 增加"疑问词+看"的正则兜底：`看.*(吗|什么|啥|东西|人)` 形式且主语指向狗（含"你"或无前缀命令式）时判为视觉问句。
- 误伤保护：含运动词（走/转/坐/趴/停）的句子优先走快速指令，不进视觉。

**B. dashboard /api/chat 接入视觉**

- 在 dashboard.py 的 `/api/chat` 处理中，先过 `is_vision_query(text)`：
  - 命中 → 调用同一个 `VisionClient.look()`（复用 8094/snapshot 取帧）→ 返回 `{"reply": 描述, "vision": true}`；
  - 未命中 → 维持原 LlmDialogue 路径。
- 前端可在回复气泡上加个"📷"标记表示回答来自实时画面（可选）。

**C. 可观测性**

- 视觉问答每次触发在日志打一行：`[VISION] query='...' hit=<短语> latency=6.1s`。
- 未命中的"疑似视觉问句"（含"看"但没落表）也打日志，方便赛后补充词表。

### 改动点

- `integrated_system/vision_assistant.py`：扩 VISION_PHRASES + 正则兜底 + 日志
- `integrated_system/dashboard.py`：/api/chat 增加视觉分支
- 轻量版注意：8094 不推流时视觉不可用，/api/chat 应返回"轻量模式未开摄像头画面"而非报错

### 验证

1. `python3 vision_assistant.py "你看到了吗"` 直通测试。
2. 语音："小狗"→"你能看见我吗" → 应回答画面内容。
3. 网页 8081 对话框输入"你现在能看到什么" → 返回实时画面描述。
4. 回归：说"坐下""往前走"不应触发视觉。

## P0-2 手势识别误触发（手一挥过狗就动）

### 诊断

`gesture_control.py` 的 `ActionScheduler.update()`：**单帧命中立即触发**。
`gesture_hold_sec=0.5` 只用于"手势消失多久后停车"，对激活没有任何门槛。
MediaPipe 对手快速经过画面时会把瞬态手势误分类成 palm/thumb_up，于是狗突然前进或坐下。

### 方案（激活确认 + 保持现状的即时停车）

1. **连续帧确认**：同一手势需连续出现 N 帧（建议 N=6，10fps 下约 0.6s）才激活动作；
   手势变化则计数清零。停车保持现状（无手势即停），保证安全响应不变慢。
2. **离散动作加冷却复用现有 action_lock**（已有 2.5s，保留）。
3. **可选"激活手势"模式**（比赛演示更稳）：只有先比出指定手势（如 thumb_up 保持 1 秒）
   进入"受控状态"后，其他手势才生效；无手势 5 秒自动退出受控状态。
   用 `--require-activation` 开关，默认关。
4. 参数化：`--confirm-frames 6` 命令行可调，start_all.sh 里按需加大。

### 改动点

- `standalone/gesture_control.py`：ActionScheduler 增加确认计数器（约 20 行）
- `standalone/gesture_control_lite.py`：同步（轻量版共用逻辑，注意保持一致）
- 推送 GitHub 后现场可直接 `--confirm-frames` 调参

### 验证

1. 手在镜头前快速挥过（<0.5s）→ 狗不动。
2. 稳定比 palm 1 秒 → 前进；手放下 → 0.5s 内停车。
3. 连续切换不同手势 → 不应连续触发多个动作。

## P1-1 语音抗噪

### 现状

日志里大量 `[VAD] 超时` / `（没听到）`：噪音触发 VAD 但 ASR 无结果，或环境人声误唤醒。
当前参数：VAD aggressiveness=2、min_speech_frames=6、增益 10dB。

### 方案（按成本从低到高，先做 1-3）

1. **参数收紧**（零成本，先试）：
   - aggressiveness 2→3（最严格档）
   - min_speech_frames 6→10（约 300ms 连续人声才进入识别）
   - 录音增益 10→6dB（降低底噪放大）
2. **TTS 后静默窗口**：播报完成后 300~500ms 内不开 VAD，防止喇叭余音自触发。
   （当前已是半双工：speak() 阻塞后才录音，只需加 settle 延时）
3. **sox 降噪预处理**（轻量）：录音后加 `highpass 200` + `compand` 噪声门，
   滤低频轰隆和小于阈值的杂音；不需要训练模型，CPU 开销可忽略。
4. **（可选，谨慎）RNNoise**：效果好但 X5 上要占 ~10% CPU，与"低负载"目标冲突，比赛环境噪音大时再考虑。
5. **硬件层**（最有效）：麦克风尽量远离喇叭、加海绵防风罩、指向性麦头朝向操作者。

### 验证

- 在嘈杂环境（放音乐/多人说话）连续 5 分钟，统计误唤醒次数（目标：≤1 次）。
- 正常音量说话识别率不下降（目标：10 句唤醒 ≥9 次）。

## P1-2 启动时间与运行延迟优化

### 现状

- `start_all.sh` 串行启动 7 个组件，含多处固定 `sleep` 等待；Vosk 模型与 sherpa TTS 加载各需数秒；整机 load average 20+。

### 方案

1. **就绪轮询替代固定 sleep**：UDP 5005/5006 已有就绪检测，把其余 sleep 改为
   轮询端口/topic 就绪（超时兜底），预计省 10~20s。
2. **非关键组件延后**：dashboard、手势画面推流等对"能演示"非关键的组件放到最后，
   语音+避障优先就绪。
3. **模型预热检查**：Vosk/sherpa 模型文件在 SD 卡上，首次读慢；可在启动脚本前加
   `cat model > /dev/null` 预热页缓存（ reboot 后第一次启动提速明显）。
4. **延迟优化（已完成项）**：VLM `enable_thinking=false`（11s→6s）、快速指令绕过 LLM、
   轻量版裁视频流（CPU 43%）。**剩余空间**：
   - gesture_control 占约 1 核（~100% CPU）：加 `--proc-fps 10` 或分辨率 640×480→480×360；
   - 3 路 mjpeg_bridge 合计 ~125% CPU：不需要演示画面时降帧或临时关闭。
5. **CPU 调度**：确认 `performance` 调度器（`cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor`）。

### 验证

- 从 `./start_all.sh start` 到"语音可唤醒"计时（目标：比现在少 30%+）。
- `uptime` load average 对比；语音问答端到端（说完→播报）秒表计时。
