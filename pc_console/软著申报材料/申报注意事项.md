# 软著申报注意事项与自查清单

> 针对你担心的"代码是 AI 写的会不会不好通过"这个问题，
> 本文件给出事实层面的分析和申报前的自查清单。

---

## 一、关于"AI 写的代码"——先说结论：这不是登记环节的风险点

### 1. 软著登记实行"形式审查"，不是"实质审查"

中国版权保护中心的登记流程只审查**材料的完整性与格式合规性**：

- 审查员**不会运行你的代码**（登记机关没有代码执行环境）；
- 审查员**不会做 AI 生成检测**（目前没有官方 AI 检测环节，也没有
  因"疑似 AI 生成"驳回的依据和公开先例）；
- 审查员**不会做全网查重**（软著与专利不同，不查新颖性、不比对
  在先代码）。

实际驳回原因几乎全部是**格式与一致性问题**（见第三节），
材料合规的申请通过率很高。

### 2. 真正的风险点：混入第三方版权代码

登记材料里如果出现以下内容，才可能被要求补正甚至引发权属争议：

- D-Robotics / 地平线官方示例的版权声明（`Copyright (c) 2025
  D-Robotics Corporation`）
- 幻尔科技 PuppyPi SDK 代码
- ROS 社区开源包代码（gmapping、hector_slam 等，它们是 GPL/LGPL）
- 其他任何带第三方版权头或开源许可证头的代码

**本套材料已规避该风险**：源程序材料.pdf 只包含本次开发的
`pc_console/` 上位机软件代码（21 个模块、约 3700 行），不含任何
厂商 SDK、官方示例与开源第三方代码。申报时**不要**把工作区里的
`pydev_demo/`、`40pin_samples/`、`cdev_demo/`、`stereo_vision/`
等目录的代码混进鉴别材料。

### 3. AI 辅助开发的权属现状

- 现行《计算机软件保护条例》与登记实践**不审查代码的生成方式**，
  申请表也没有"是否 AI 辅助"这一栏；
- 行业普遍做法：开发者使用 AI 工具辅助编写、自己完成需求设计、
  调试修改、测试验证后，以自己（或单位）名义登记著作权；
- 项目中的**现场标定参数、中文注释、业务逻辑设计（如运动仲裁
  优先级、长按心跳机制、避障状态机阈值）都是人工决策的痕迹**，
  这正是"AI 辅助 + 人工创作"的证明。

**建议**：保留开发过程记录（git 提交历史、调试日志、需求笔记），
权属上有备无患，但不需要主动提交。

## 二、材料格式规范（已按规范生成，复查用）

### 源程序鉴别材料
- [x] 前 30 页 + 后 30 页，共 60 页（代码总量超过 60 页时）
- [x] 每页 50 行（含长行折行）
- [x] 每页页眉标注软件全称及版本号
- [x] 每页页脚标注页码（第 X 页 共 60 页）
- [x] 首页从程序第一行开始，末页为程序结束
- [x] 代码中无第三方版权头、无注释掉的成段废弃代码

### 文档鉴别材料（用户操作手册）
- [x] 内容与软件实际功能一致（每个功能模块有操作步骤）
- [x] 含界面截图
- [x] 页眉标注软件全称及版本号、页脚页码
- [x] 总页数不足 60 页 → 全部提交（符合"不足 60 页的全部提交"规则）

### 申请表
- [ ] 软件全称与两份 PDF 页眉**完全一致**（一个字都不能差）
- [ ] 版本号 V1.0 与页眉一致
- [ ] 开发完成日期不晚于首次发表日期
- [ ] 著作权人名称与身份证明文件完全一致

## 三、常见驳回/补正原因对照自查

| 常见驳回原因 | 本套材料状态 |
|---|---|
| 页眉未标注软件名称及版本号 | 已规避（每页均有） |
| 每页代码不足 50 行 | 已规避（固定 50 行/页） |
| 源程序与文档描述的软件名称不一致 | 三处统一为同一名称，申报时勿手改其一 |
| 文档与软件功能不符 | 手册按实际功能模块逐章编写 |
| 名称使用违禁词/通用词/含商标 | "机器狗远程监控与运动控制上位机软件"含具体功能限定 |
| 表格填写不全/签章缺失 | 赛前与官方代办确认署名方式后补齐 |
| 材料乱码 | 全部 UTF-8 中文，PDF 已内嵌字体 |

## 四、申报流程建议

1. **确定署名方式**（个人 / 学校）→ 确定"开发方式"字段；
2. 将以下材料交给比赛官方代办（或自行在
   www.ccopyright.com.cn 注册提交）：
   - 源程序材料.pdf
   - 用户操作手册.pdf
   - 申请表信息（见《软著申请表信息.md》）
   - 身份证明（个人身份证复印件 / 学校法人证书）
3. 提交后约 1~2 个工作日进入受理状态，可在官网查询进度；
4. 若收到补正通知（最常见：名称不一致、页数行数问题），按通知
   小范围修改后重新提交即可，**补正不影响最终登记**。

## 五、答辩/演示场景的额外建议

- 演示软件时优先用演示模式（`python main.py --demo`），不依赖
  板端与网络，任何场地都能稳定运行；
- 若评委问及开发过程，可展示 git 历史（`git log --stat`）说明迭代
  过程，并说明网络协议层、线程模型、仲裁心跳等设计决策；
- 软件著作权保护的是**代码的表达形式**，比赛答辩重点讲功能与
  设计即可。

## 六、材料再生成方法

若软件后续迭代（代码变更、界面调整），在项目根目录执行：

```bash
# 1. 重新采集界面截图（演示模式）
QT_QPA_PLATFORM=offscreen python3 tools/capture_screenshots.py screenshots

# 2. 重新生成两份 PDF 材料
QT_QPA_PLATFORM=offscreen python3 tools/generate_materials.py
```

Windows 下去掉命令前的 `QT_QPA_PLATFORM=offscreen ` 前缀直接运行即可。

> 注意：代码变更超过一定幅度后属于新版本，如需登记 V1.1/V2.0
> 应重新提交全套材料（版本升级登记与首次登记流程相同）。
